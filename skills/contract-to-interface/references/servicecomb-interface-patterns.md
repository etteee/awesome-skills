# Apache ServiceComb Java Chassis interface patterns

This note turns the Java Chassis 3 provider and consumer documentation into source-level recognition rules for commit-time contract enforcement. It distinguishes documented framework behavior from the detector recommendations derived from that behavior. Sources are limited to Apache ServiceComb documentation and Apache ServiceComb repositories.

## Version and namespace caution

The Java Chassis 3 JAX-RS guide still lists `javax.ws.rs.*` annotations, including `Path`, `Produces`, HTTP-method annotations, and parameter annotations.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) The current Apache Java Chassis source examples at commit `ac4a6991e6334607b786607ad1e60638ff6ad4bf` import the corresponding `jakarta.ws.rs.*` types.[Current JAX-RS interface source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-jaxrs/jaxrs-server/src/main/java/org/apache/servicecomb/demo/jaxrs/server/SchemeInterfaceJaxrs.java#L18-L38) A source checker intended to work across Java Chassis 3 projects should therefore recognize both `javax.ws.rs` and `jakarta.ws.rs`; matching only an annotation's simple name is unsafe because the namespace is version-sensitive.

The ServiceComb annotations and consumer helpers have these fully qualified names in the same first-party source revision:

| Simple name | Fully qualified name | Source-level facts |
|---|---|---|
| `RestSchema` | `org.apache.servicecomb.provider.rest.common.RestSchema` | Runtime type annotation; `schemaId` is required and `schemaInterface` defaults to `Object.class`.[Source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-rest-common/src/main/java/org/apache/servicecomb/provider/rest/common/RestSchema.java#L18-L39) |
| `RpcSchema` | `org.apache.servicecomb.provider.pojo.RpcSchema` | Runtime type annotation; both `schemaId` and `schemaInterface` have defaults.[Source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/RpcSchema.java#L18-L39) |
| `RpcReference` | `org.apache.servicecomb.provider.pojo.RpcReference` | Runtime annotation allowed on fields, methods, and annotation types; `microserviceName` is required and `schemaId` defaults to the empty string.[Source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/RpcReference.java#L18-L35) |
| `RestTemplateBuilder` | `org.apache.servicecomb.provider.springmvc.reference.RestTemplateBuilder` | `create()` returns Spring's `org.springframework.web.client.RestOperations`.[Source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-springmvc/src/main/java/org/apache/servicecomb/provider/springmvc/reference/RestTemplateBuilder.java#L18-L30) |
| `Invoker` | `org.apache.servicecomb.provider.pojo.Invoker` | `createProxy(microserviceName, schemaId, consumerIntf)` creates a dynamic proxy implementing the supplied interface class.[Source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/Invoker.java#L18-L64) |

Both provider annotations are Java `@Inherited` annotations, and current registration code reads them with `Class.getAnnotation(...)`; direct annotations and annotations inherited from a superclass are therefore positive roots.[REST registration source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-rest-common/src/main/java/org/apache/servicecomb/provider/rest/common/RestProducers.java#L57-L77) [RPC registration source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/schema/PojoProducers.java#L52-L79) Although their `@Target` includes `ANNOTATION_TYPE`, the registration code does not by itself establish recursive meta-annotation discovery; a checker should not treat an arbitrary composed annotation as a provider root without repository-specific evidence.

## Provider recognition

### Strong provider roots

| Pattern | What it identifies | Published surface |
|---|---|---|
| A class annotated with `@RestSchema` | A JAX-RS or Spring MVC provider implementation. The JAX-RS guide annotates its implementation with `@RestSchema`, `@Path`, and HTTP-method annotations; the Spring MVC guide uses `@RestSchema` plus Spring mapping annotations.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) [Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html) | Without a constraining `schemaInterface`, Java Chassis scans the implementation's methods and publishes its public methods.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html) |
| A class annotated with `@RpcSchema` | A transparent-RPC provider implementation. Transparent RPC is based on a Java interface plus an implementation and does not require JAX-RS or Spring MVC annotations.[Transparent RPC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/transparent-rpc.html) | Without a constraining `schemaInterface`, the general public-method scan rule applies.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html) |
| `@RestSchema(schemaInterface = I.class)` or `@RpcSchema(schemaInterface = I.class)` on an implementation that implements `I` | `I` is the authoritative provider schema interface. The attribute exists on both ServiceComb annotations.[`RestSchema` source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-rest-common/src/main/java/org/apache/servicecomb/provider/rest/common/RestSchema.java#L31-L39) [`RpcSchema` source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/RpcSchema.java#L31-L39) | Only methods in `I` are published; an additional public implementation method is not published.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html) |
| An interface bearing JAX-RS routing annotations such as `@Path` and an HTTP-method annotation, or Spring MVC mappings such as `@RequestMapping`/`@GetMapping` | A REST schema interface candidate. Both provider guides show routing annotations on an interface; interface declaration is optional unless it is selected as `schemaInterface`.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) [Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html) | Treat it as definitely published only after linking it to a provider implementation or generated contract; annotations alone can exist in shared API modules. This last qualification is a detector recommendation, not a documented runtime rule. |

Spring MVC also permits `org.springframework.web.bind.annotation.RestController` as a service declaration equivalent to a default `RestSchema` schema id, but scanning can be disabled with `servicecomb.provider.rest.scanRestController=false`.[Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html) For commit enforcement, classify `@RestController` as a provider root only after checking that configuration; otherwise report it as a candidate rather than a certainty.

When `@RpcSchema.schemaId` is empty, current registration code derives the schema id from the sole implemented interface's fully qualified name; zero or multiple implemented interfaces are rejected.[RPC provider registration source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/schema/PojoProducers.java#L52-L79) A checker must therefore resolve implemented interfaces before deciding the effective schema identity.

### `schemaInterface` changes annotation ownership

When `schemaInterface` is used, JAX-RS, Spring MVC, and Swagger/OpenAPI annotations must be declared on the schema interface; putting those annotations only on the implementation is ineffective.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html) This creates a precise enforcement rule:

1. Resolve the class literal assigned to `schemaInterface`.
2. Read operation/path/parameter annotations from that interface and its method declarations, not from the implementation.
3. Compute the exposed method set from the interface; do not add implementation-only public methods.
4. Require the implementation to implement the selected interface, matching the documented pattern.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html)

Without `schemaInterface`, a generic implemented Java interface is not by itself a complete description of the published REST surface: the guides show optional unannotated business interfaces while routing annotations remain on the implementation, and Java Chassis publishes implementation-specific public methods too.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) [Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html)

### REST operation annotations

For JAX-RS providers, the documented contract-bearing annotations are `Path` and `Produces` at schema or operation level; `DELETE`, `GET`, `POST`, and `PUT` at operation level; and `QueryParam`, `PathParam`, `HeaderParam`, `CookieParam`, `FormParam`, and `BeanParam` at parameter level.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) An unannotated non-context parameter is treated as a body parameter, with at most one body parameter per method; `HttpServletRequest` and `InvocationContext` are exceptions to that default.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html)

For Spring MVC providers, Java Chassis documents support for `RequestMapping`, `GetMapping`, `PutMapping`, `PostMapping`, `DeleteMapping`, `PatchMapping`, `RequestParam`, `CookieValue`, `PathVariable`, `RequestHeader`, `RequestBody`, `RequestPart`, and `RequestAttribute`, while several Spring MVC annotations such as `ResponseBody`, `ResponseStatus`, and `ModelAttribute` are not supported as normal contract controls.[Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html) In particular, ServiceComb interprets `RequestParam` as a query parameter and `RequestAttribute` as a form parameter.[Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html)

The current official repository demonstrates the Spring annotations under `org.springframework.web.bind.annotation.*`, OpenAPI v3 `Operation` under `io.swagger.v3.oas.annotations.Operation`, and JAX-RS annotations under `jakarta.ws.rs.*`.[Spring MVC source example](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-springmvc/springmvc-server/src/main/java/org/apache/servicecomb/demo/springmvc/server/WeakSpringmvc.java#L18-L56) [JAX-RS/OpenAPI source example](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-schema/src/main/java/org/apache/servicecomb/demo/api/IHeaderParamWithListSchema.java#L18-L41)

### Swagger/OpenAPI annotations

Spring MVC or JAX-RS annotations supply the basic REST contract, while Swagger/OpenAPI annotations supplement details; where they overlap, the Swagger/OpenAPI description has higher priority.[Swagger annotation guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/swagger-annotation.html) The guide specifically uses:

- `io.swagger.v3.oas.annotations.OpenAPIDefinition` on an interface/type for tags or a server/base-path prefix.[Swagger annotation guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/swagger-annotation.html) [Current first-party usage](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-pojo/pojo-server/src/main/java/org/apache/servicecomb/demo/pojo/server/same/pk1/SameInterface.java#L18-L26)
- `io.swagger.v3.oas.annotations.Operation` on a method to set `operationId` or descriptive metadata.[Swagger annotation guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/swagger-annotation.html) [Current first-party usage](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-springmvc/springmvc-server/src/main/java/org/apache/servicecomb/demo/springmvc/server/WeakSpringmvc.java#L31-L56)
- `io.swagger.v3.oas.annotations.Parameter` and `io.swagger.v3.oas.annotations.enums.{ParameterIn,ParameterStyle,Explode}` to describe parameter location and collection serialization.[Swagger annotation guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/swagger-annotation.html) [Current first-party usage](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/demo/demo-schema/src/main/java/org/apache/servicecomb/demo/api/IHeaderParamWithListSchema.java#L20-L41)

The RPC consumer guide also contains the older Swagger 2 `@ApiOperation(nickname = "...")` form for mapping a differently named reactive method to an existing `operationId`.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html) A version-tolerant checker should resolve imports and support both `io.swagger.v3.oas.annotations.Operation(operationId=...)` and legacy `io.swagger.annotations.ApiOperation(nickname=...)`, rather than conflating their attribute names.

## Consumer recognition

### RPC consumers

A plain Java interface becomes a positive RPC-consumer interface when used as the type of an `@RpcReference(microserviceName=..., schemaId=...)` injection point, or when supplied as the third class-literal argument to `Invoker.createProxy(microserviceName, schemaId, Interface.class)`.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html) The provider need not use the same Java interface or even the same provider programming style; consumer RPC is independent of provider use of transparent RPC, JAX-RS, or Spring MVC.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html)

`@RpcReference` is valid on both fields and methods.[`RpcReference` source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/RpcReference.java#L18-L35) The framework takes the field type for field injection and the first method-parameter type for method injection, then configures that type as the consumer interface.[Reference processor source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/reference/RpcReferenceProcessor.java#L49-L90) Commit-time detection should therefore resolve both forms.

When `@RpcReference.schemaId` is empty, current consumer lookup falls back to the consumer interface's fully qualified name.[Consumer lookup source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/PojoConsumerMetaRefresher.java#L164-L172) The effective interface-to-schema mapping can therefore depend on a Java package or interface rename even when the annotation text is unchanged.

RPC consumer interfaces require no REST annotations.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html) Their methods map to contract operations by method name/`operationId`; reactive return values use `CompletableFuture<T>`, and an alternate Java method name must explicitly map back to the contract operation id because Java cannot overload solely on return type.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html)

### `RestOperations` consumers

`RestTemplateBuilder.create()` supplies a ServiceComb `RestOperations` instance, and calls such as `getForObject` and `postForObject` use a logical ServiceComb URL rather than a concrete host address.[RestOperations consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/using-resttemplate.html) The current guide documents `servicecomb://microserviceName/path?querystring`; other official provider examples still use `cse://...`, so a repository-wide detector should accept both prefixes when recognizing legacy and current client calls.[RestOperations consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/using-resttemplate.html) [JAX-RS provider guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) [Spring MVC provider guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html)

This consumer style does **not** identify a Java consumer interface. Instead, each call site exposes:

- the target service/path/query in the ServiceComb URL;
- a request-body value where the selected `RestOperations` method has one; and
- a response type such as `String.class` or `Person.class`.[RestOperations consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/using-resttemplate.html)

For enforcement, resolve the call to the `RestOperations` instance produced by ServiceComb's `RestTemplateBuilder`, rather than matching any variable named `restTemplate` or every Spring `RestOperations` call. Its wrapper delegates non-ServiceComb URLs to a default Spring `RestTemplate`, so receiver provenance plus the `servicecomb://` or `cse://` scheme is the strong ServiceComb-call signal.[Wrapper source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-springmvc/src/main/java/org/apache/servicecomb/provider/springmvc/reference/RestTemplateWrapper.java#L42-L73) The helper's actual return type is `RestOperations`, even though one documentation example declares a `RestTemplate` variable.[Builder source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-springmvc/src/main/java/org/apache/servicecomb/provider/springmvc/reference/RestTemplateBuilder.java#L18-L30) [RestOperations consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/using-resttemplate.html)

## DTO and signature closure

Once a provider operation or RPC consumer interface is identified, enforce changes over the transitive contract-type closure, not only over the top-level interface file. The closure should begin with every operation parameter and return type, unwrap arrays/collections/maps, retain every concrete generic argument, and follow fields or JavaBean properties of application DTOs. This detector rule follows from Java Chassis generating OpenAPI from all interface definitions and from its documented requirement for explicit, platform-independent data shapes.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)

Transport and response wrappers need semantic unwrapping. For example, the RPC guide defines `CompletableFuture<T>` as a reactive return whose contract payload is `T`, while the Spring MVC guide shows a ServiceComb `Response` whose actual response type is supplied by `@ApiResponse(response = User.class)`.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html) [Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html) Include explicit Swagger/OpenAPI response/schema class literals in the DTO roots when the Java return wrapper hides the payload type.

The documented type constraints relevant to that closure are:

- Prefer concrete, platform-independent types. `Object`, JSON-object abstractions, interfaces, abstract classes, their collections, raw `List`/`Map`, and wildcard-like unresolved shapes are not best-practice contract types; `List<String>` and `List<Person>` are supported concrete collections.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
- OpenAPI arrays must have an element type, and map keys must be strings.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
- Provider return signatures must preserve complete generic information, for example `Holder<List<Person>>` rather than raw `Holder`; otherwise the generated contract lacks the element type and consumers can receive maps instead of `Person` objects.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
- DTOs should conform to JavaBean property naming. Inconsistent fields and accessors can generate unstable contract properties; `@JsonPropertyOrder` can explicitly stabilize order.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
- Public external contracts should prefer custom POJOs to third-party classes, because dependency upgrades can change a third-party type without an obvious source edit in the service.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
- REST-only support for interface or abstract types requires a Jackson type extension plus `ConcreteTypeRegister`, and the extension must be present in consumer, provider, and edge service.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)

Parameter-aggregation rules require special handling:

- A JAX-RS `@BeanParam` type must be a standard JavaBean. Parameter annotations may be placed on fields or setters; extra complex properties must be ignored with `@JsonIgnore`; body parameters cannot be aggregated. Consumers still send the expanded contract parameters separately.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html)
- An unannotated Spring MVC POJO parameter can aggregate query parameters only when it has no Spring parameter annotation; property names become query names; nested POJOs/lists are unsupported unless ignored with `@JsonIgnore`; consumers again use the expanded query parameters rather than the provider POJO wrapper.[Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html)

Consequently, an aggregation-only wrapper is a provider-side binding type, not necessarily a wire DTO or a consumer-interface parameter. Enforcement should compare its expanded parameter projection with the contract and should not demand that RPC consumers reuse the wrapper.[JAX-RS guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/jaxrs.html) [Spring MVC guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/springmvc.html)

## Commit-time enforcement recipe

The following is a recommended static-analysis policy derived from the documented behavior above:

1. Resolve imports and annotation types; do not recognize ServiceComb patterns by simple names alone.
2. Index provider roots: `@RestSchema`, `@RpcSchema`, and configuration-enabled `@RestController` classes.
3. If `schemaInterface` is explicit, make that interface the sole published method root and read REST/OpenAPI annotations there. Otherwise, inspect every public method of the provider implementation because that is the default publication rule.[Interface-only publication guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/use-interface.html)
4. Index RPC consumer roots from `@RpcReference` field types, `@RpcReference` method first-parameter types, and `Invoker.createProxy(..., Interface.class)` class literals.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html) [Reference processor source](https://github.com/apache/servicecomb-java-chassis/blob/ac4a6991e6334607b786607ad1e60638ff6ad4bf/providers/provider-pojo/src/main/java/org/apache/servicecomb/provider/pojo/reference/RpcReferenceProcessor.java#L49-L90)
5. Index ServiceComb REST consumer calls through data flow from `RestTemplateBuilder.create()` and extract URL, request type, and response type per invocation.[RestOperations consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/using-resttemplate.html)
6. Build the transitive DTO closure with full generic arguments, unwrap reactive/transport wrappers, and add explicit Swagger/OpenAPI payload class literals. Treat parameter location, path, HTTP method, operation id, parameter name/order/type, return type, DTO property name/type, and collection element type as contract-affecting data. Java Chassis explicitly classifies interface name, parameter type, parameter order, and return type changes as interface changes and detects changes from generated contract content.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
7. Fail closed when a changed type in the closure is raw, abstract, an interface, or otherwise cannot be projected deterministically, unless the repository contains the documented REST type-extension registration.[Interface and data-type guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-provider/interface-constraints.html)
8. Do not infer a ServiceComb interface from naming conventions such as `*Api`, `*Service`, or `*Client`. The official RPC consumer model intentionally uses plain, annotation-free Java interfaces, so a reference site or provider linkage is the reliable positive signal.[RPC consumer guide](https://servicecomb.apache.org/references/java-chassis/zh_CN/build-consumer/develop-consumer-using-rpc.html)
